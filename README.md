# Оператор входящих заказов (OpenClaw-агент)

Агент разбирает входящие фриланс-заказы и показывает по каждому: **откликаться**, **на проверку**
или **пропустить** — с причиной и, где возможно, готовым черновиком отклика. Надстройка над ядром
[AI Freelance Copilot](https://github.com/Alexsey111/AI_Freelance_Copilot), а не замена ему:
оценки и решения считает ядро, агент оркеструет разбор и объясняет результат человеку.

## Зачем

Владелец разбирает заказы вручную: поиск и чтение ~1 мин, оценка своих возможностей, сроков и
цены — 5–10 мин (в среднем 7). Это ~8 минут на заказ. Агент снимает эту рутину: заливка заказов,
прогон через ядро, понятная сводка «что брать, что проверить, что пропустить», а по расписанию —
готовый отчёт по новым заказам и очереди ручной проверки.

## Что делает

| Умение | Команда | Результат |
|---|---|---|
| Разобрать **один** заказ | `python scripts/orders_ops.py order --external-id fl-2411-001` | решение, причина, черновик → `reports/latest-order.md` |
| Проверить связь с ядром | `python scripts/orders_ops.py health` | статус, провайдер, тратит ли деньги |
| Залить заказы в ядро | `python scripts/orders_ops.py ingest` | идемпотентно, без дублей |
| Разобрать пачку заказов | `python scripts/orders_ops.py triage --analyze --only-new` | `reports/latest-triage.md` |
| Очередь проверки | `python scripts/orders_ops.py queue` | что ждёт решения человека |
| Сводка (по расписанию) | `python scripts/orders_ops.py summary` | `reports/daily-summary.md` |
| Сквозные сценарии | `python scripts/orders_ops.py test` | `tests/results.json` |

## Прогон 20 заказов на реальной модели (03.11.2026)

Проверялось на отдельной базе прогона (`data/live.db` ядра): 20 заказов, 20 анализов,
модель `gpt-4o-mini` через proxyapi, 0 ошибок, все ответы — валидный JSON. Профиль исполнителя
настоящий, не заглушка: 13 навыков, минимум 50 000 ₽, список «чего не беру»
(`scripts/seed_profile.py` ядра, файл `data/profile.json`).

| | вручную | с агентом |
|---|---|---|
| на один заказ | 8 мин (замер владельца: 1 мин поиск + 7 мин оценка) | 2,1 с машинного времени |
| на 20 заказов | 160 мин | 43 с |
| стоимость | — | 1,37 ₽ за прогон (0,07 ₽ на заказ) |
| уходит человеку | всё | 4 из 20 решений (20 %) |

- **8 минут** на заказ вручную — замер владельца на реальном заказе FL.ru.
- **2,1 секунды** на заказ с агентом: 20 заказов = 43,2 с, медиана 2 011 мс, максимум 3 996 мс.
- **1,37 ₽** за прогон 20 заказов: 24 666 входных и 2 624 выходных токена, тариф proxyapi
  39 / 155 ₽ за 1 млн токенов с НДС (`scripts/measure_cost.py` ядра, usage из ответа провайдера).
- **4 из 20 (20 %)** ушли на проверку человеку: 8 «откликаться», 4 «на проверку», 8 «пропустить».

Что остаётся человеку: 4 записи очереди и 8 черновиков. Время этой части не замерено —
в ядре стоит оценка из ТЗ (3 мин на заказ), владельцем она не проверялась, поэтому в таблице её нет.

### Что нашёл живой прогон — и что после этого исправлено

1. **Прогон шёл против профиля-заглушки.** В ядре лежал профиль по умолчанию: минимум 20 000 ₽,
   без списка «чего не беру», без preferred-стека. Модель не знала ограничений владельца и
   предлагала брать заказы за 20–45 тыс. рублей. Исправлено: `scripts/seed_profile.py` +
   `data/profile.json` заполняют активный профиль настоящими данными; предпочтения попадают
   в промпт, и отказы по чужому стеку модель делает сама (React-вёрстка и SEO → «пропустить»).
2. **Бюджет ниже минимума профиля не отсекался.** Заказ `fl-2411-012` (20 000 ₽) получал
   «откликаться» с готовым черновиком, `fl-2411-007` (45 000 ₽) — тоже. Исправлено правилом
   ядра `budget_below_profile_minimum`: если верхняя граница бюджета ниже `min_budget_rub`,
   решение — «пропустить», и это решает система, а не модель. Пять новых тестов, полный
   `pytest` зелёный (125).
3. **Пограничные случаи остаются человеку — так требует ТЗ §14.3.** Заказ `fl-2411-019`
   (дашборды) ушёл в «на проверку» не потому, что система сломалась, а потому что модель
   честно сомневается. Это осознанная цена, а не дефект: попытка автоматически превращать
   такие «на проверку» в «пропустить» ломает сценарий `S11_analytics_borderline` из набора ТЗ.

Итог по очереди: до правок 7 записей (35 %), после — 4 (20 %). Из четырёх три — «не указан
бюджет» и один пограничный.

Повторяемость: второй прогон тем же кодом на копии базы дал те же 20 решений из 20.
Разброс по времени между прогонами — 38–43 секунды: это задержка сети провайдера, решения не меняются.

### Как проверить

```bash
# ядро — отдельная база прогона, реальный провайдер (ключ в .env, в репозиторий не попадает)
# проще всего: двойной щелчок по scripts\run_live.cmd
# из PowerShell:   cd "D:\python projects\AI_Freelance_Copilot"; .\scripts\run_live.ps1
# в bash:          DATABASE_URL="sqlite:///./data/live.db" LLM_PROVIDER=openai \
#                    ./.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8800
cd "D:/python projects/AI_Freelance_Copilot"
DATABASE_URL="sqlite:///./data/live.db" ./.venv/Scripts/python.exe scripts/seed_profile.py

# агент
cd "D:/python projects/openclaw-orders-agent"
python scripts/orders_ops.py ingest
python scripts/orders_ops.py --timeout 180 triage --analyze --limit 25
python scripts/orders_ops.py queue
python scripts/orders_ops.py summary
```

Данные прогона лежат в `reports/run-2026-11-03-live.json` (по каждому заказу: оценка,
решение, причина проверки, длительность, решение повторного прогона), отчёт —
`reports/latest-triage.md`.

Ограничение замера: ядро не пишет `usage` из ответа модели в журнал аудита, поэтому
токены и рубли сняты отдельным скриптом на копии базы, а не из самого прогона.
Одношаговое улучшение — сохранять `prompt_tokens` / `completion_tokens` в `audit_runs`.

## Тот же разбор без Python: n8n (03.11.2026)

Тот же прогон 20 заказов, но не скриптом, а визуальным workflow в n8n (self-hosted, Docker,
каталог `n8n/`). Ядро остаётся единственным местом, где живут правила и вызов модели:
workflow только дёргает его API по одному заказу.

| Что сравниваем | Python-мост (`orders_ops.py`) | Workflow n8n |
|---|---|---|
| Заказов разобрано | 20 | 20 |
| Решения | 8 apply / 4 review / 8 skip | 8 apply / 4 review / 8 skip |
| Очередь проверки | 4 | 4 |
| Время | 38–43 с | 41,5 с |
| Ошибок модели | 0 | 0 |

Совпадение неслучайно: правила и промпт одни и те же, потому что оба пути ходят в одно
ядро. Разница только в способе управления — код и тесты против узлов и мыши.

Что выяснилось на практике:

- n8n в Docker не видит `127.0.0.1` хоста, только `host.docker.internal`.
- Параллельные запросы валят SQLite ядра (`database is locked`), поэтому обход заказов
  идёт по одному: Loop Over Items, batch size 1.
- В Loop Over Items v3 выходы перепутаны относительно привычного порядка: первый выход —
  «готово» (пустой), второй — батч. Из-за этого первый вариант workflow молча разбирал
  ноль заказов и заканчивался «успехом».
- Один вызов модели из двадцати упал по таймауту 90 с. Ядро не уронило прогон,
  а отправило заказ в очередь проверки — fail-safe сработал как задумано.

Запуск и оговорки: `n8n/README.md`.

## Сводка по заказам: когда она нужна

Новые заказы в этой системе появляются только вручную: единственный источник заказов
в ядре — `manual`, парсинг площадок не реализован (ТЗ §22). Поэтому сводка «по расписанию»
не может сообщить ничего нового: пока машина выключена, заказов не возникает, а когда
включена — их приносит человек.

Правильный порядок — в конце рабочей сессии с копилотом, когда ядро уже поднято, а заказы
разобраны:

```bash
python scripts/orders_ops.py summary     # → reports/daily-summary.md
```

Запуск при входе в систему (`Orders Agent Summary (logon)` → `scripts/daily_summary.cmd`)
снят 2026-11-02 по решению владельца: задача вызывала сводку, сводка требует живого ядра,
а ядро при входе никто не поднимает — 0 успешных запусков из 10. Журнал оставлен как
история: `reports/logon-summary.log`, разбор — DEF-021 в репозитории приёмки.

Cron-задача OpenClaw `0 8 * * *` остаётся частью сдачи проекта, но новых данных она
не даёт по той же причине: срабатывает, когда компьютер выключен.

Интерпретатор — `python`, не `python3`: на Windows имя `python3` перехватывает заглушка
Microsoft Store и скрипт не выполняется.

## Важно

- Агент **ничего не отправляет** заказчикам: автоотправка откликов в ядре не реализована намеренно
  (ТЗ §22), и агент эту границу не расширяет.
- Агент **не правит данные ядра напрямую** — только через API.
- Решение «на проверку» не отменяется: сомнение системы передаётся человеку как есть.
- Приватность: в репозитории нет ключей и токенов; адрес ядра — локальный (`127.0.0.1`).
